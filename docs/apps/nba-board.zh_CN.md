# NBA 比赛看板应用

NBA 比赛看板把 AI Passport 变成随身记分牌:拉取某个 NBA 比赛日的比分,在深色
记分牌风格的界面上列出各场比赛,可进入单场详情查看分节得分,再进入球员页逐队翻看
12 项技术统计。比赛日可以按天往前/往后翻,不限于「今天」。

本文描述的是替换 `main/` 里基线硬件自检菜单的应用。基线 demo 源码仍留在仓库里作为
BSP 用法参考,但已不再编进固件。

## 界面与按键

| 页面 | 内容 | 按键 |
| --- | --- | --- |
| 总览 | 最多 16 场、一屏 4 行;队名缩写、比分、状态(节次+剩余时间 / 已结束 / 开赛时间) | 上/下:移动选择(循环);确定:进入详情;长按上/下:切到前/后一个比赛日;长按确定:立即刷新(没网可用时改为重新配网) |
| 详情 | 两队缩写、大字比分、战绩、分节比分(Q1–Q4、总分)、比赛状态、比赛日 | 上/下:切换比赛;确定:进入球员页;长按确定:返回总览 |
| 球员 | 顶部两队总分;队头一行(客队/主队 + 缩写 + 全队总分),往下是该队球员,一屏 8 行。名字列固定,右侧 3 列数据按确定键一组组滑过去 | 上/下:移动光标(循环);确定:滑到下一组数据列(不自动翻页);长按上:主队;长按下:客队;长按确定:返回详情 |
| 配网 | 热点名、手机要打开的地址、当前状态。在没凭据、连不上网或外网被认证页拦截时出现 | 长按确定:退出(没网可用时再长按确定可重新开热点);其余按键无效 |

### 屏幕底部的提示行

每一页的底部都有一行按键提示,但它**不罗列所有按键**——240×320 的屏幕上这一行只有
232px,16px 中文一行最多 14 字,全写只会挤到换行。取舍原则:**通行手势不写,长按才写**。
「上下选、确定进」是列表和菜单的通用心智,没人会卡住;真正猜不到的是长按。

| 页面 | 提示文案 |
| --- | --- |
| 总览(已配网且外网通) | `长按确定刷新·长按上下换日` |
| 总览(未配网 / 无法上网) | `长按确定配网` |
| 详情 | `上下换场·确定球员·长按返回` |
| 球员(两行) | `上下选人·确定换组` / `长按上下换队·长按确定返回` |
| 配网 | `长按确定返回` |

两处提示会**跟着状态变**,是刻意的:

- 总览页的长按确定在「已配网且外网通」时是刷新,在「没有凭据」或「连着 Wi-Fi
  但外网被认证页拦住」时是重新开热点。同一个键做两件完全不同的事,文案不跟着
  换就是在说假话。后一种情况尤其要标出来:Wi-Fi 明明连着,用户最容易以为设备坏了。
- 球员页是唯一需要两行的页面:三个动作(换组、换队、返回)里有 2 个是长按,单行放不下。
  代价是 8 行名单的行高从 24px 压到 22px(行卡 20px)。

提示行的宽度是按字体的 `adv_w` 实测的(`tools/check_font_coverage.py` 管字形,宽度靠
`adv_w` 逐字累加),最长的一条是详情页 224px,离 232px 上限只剩 8px —— 再想往这一行里
加字,得先删掉同样多的字。

球员页按需拉取:只有在该场详情页按下「确定」时才请求一次,同一场的结果会缓存,
再次进入不再发请求。比分随时会变,名单却很少变,没必要跟着比分刷新周期重抓。

球员页一次只显示一支球队(长按上下切换),因为一屏放不下 20 个人;数据列也放不下
12 项,所以分成 4 组轮播:

| 组 | 列 |
| --- | --- |
| 1 | 分、板、助 |
| 2 | 投、三、罚(`4-9` = 命中 4 / 出手 9) |
| 3 | 断、帽、失 |
| 4 | 时、差、犯(差 = 正负值,带 `+/-` 号) |

滑动只作用于右侧数据区:每行 3 个数字在一个裁剪窗口里整块滑出、换值、再从右侧滑入,
名字列不参与动画——翻数据时不会丢掉「这行是谁」。

换组完全由**短按确定**驱动,没有自动轮播:什么时候翻、翻几组,由看着屏幕的人决定。
(曾经做成每 3 秒自动滑一格,实际用起来会在人正盯着某一行时把数字换掉,读起来很累。)

全局行为:

- 顶栏标题右侧显示当前数据所属的比赛日(`10-31`)。不是「今天」时该日期变成琥珀色。
- 右上角显示电量。电量计无应答时角标留空,不显示假读数。
- 30 秒无按键后背光降到 22%,任意按键恢复到 100%(同时立刻刷新一次)。不做深睡:
  比赛进行期间屏幕需要一直亮着。
- 刷新间隔跟着赛程走,不再固定 60 秒;总览页长按确定、翻日、亮屏唤醒仍会立即抓取:

  | 当前显示的比赛 | 自动刷新间隔 |
  | --- | --- |
  | 有进行中 | 45 秒 |
  | 全是未开始,距最近一场开赛 >10 分钟 | 睡到开赛前 5 分钟(最长 15 分钟) |
  | 距开赛 ≤10 分钟 | 60 秒 |
  | 全是已结束 / 无比赛 | 15 分钟兜底(跨午夜自动跟上新的一天) |
  | 背光已变暗 | 以上间隔不低于 5 分钟 |
  | 未对时 / 上次抓取失败 | 60 秒 |

  每次抓取约 276KB,固定 60 秒相当于每小时白下 60 次;改成按需后,全是已结束的比赛
  每小时只抓 4 次。Wi-Fi 平时开着 modem 省电(DTIM 休眠),仅 HTTP 传输那十几秒临时
  切全速,下载速度不变。
- 需要网页认证的 Wi-Fi(校园网/酒店网)过不了:Wi-Fi 显示已连接,但网关会把所有
  HTTP 请求 302 到认证页,比分拿不到,顶栏显示「无法上网」。设备没有浏览器,无法
  完成 Portal 登录;要在认证页给设备 MAC 放行,或换手机热点这类免认证网络。
  换网不需要电脑:提示行会变成「长按确定配网」,长按即可开热点;放着不管,
  持续 3 分钟外网不通也会自动开一次热点。

## 数据来源

| 项 | 值 |
| --- | --- |
| 比分接口 | `http://site.api.espn.com/apis/site/v2/sports/basketball/nba/scoreboard?limit=16` |
| 比赛日参数 | `&dates=YYYYMMDD`(单日,美东口径);不带该参数时服务端返回「最近一个有比赛的日子」 |
| 球员接口 | `http://site.api.espn.com/apis/site/v2/sports/basketball/nba/summary?event=<event id>` |
| 鉴权 | 无 |
| 传输 | 明文 HTTP(80 端口) |
| 刷新 | 比分按赛程自适应(45 秒 ~ 15 分钟,或手动触发);球员数据按需,进入球员页时抓一次 |

### 谁在联网

是看板自己。设备开机连上已保存的 Wi-Fi(NVS 里 `nba_cfg` 存 SSID/密码),SNTP 对时,
然后由 `net_task` 直接用明文 HTTP 向 ESPN 发请求——中间没有手机、没有电脑、没有中转
服务,也不需要 API key。断网时顶栏显示「离线」并每 3 秒重试,不阻塞按键。

换 Wi-Fi 环境同样不需要电脑:旧网络连续 90 秒连不上,或者连着却持续 3 分钟
过不了网页认证,设备都会自动开热点等手机来配(见「Wi-Fi 配网」)。后者单独立了
一条看门狗——Portal 网络的 Wi-Fi 状态一直是「已连接」,走不到连接失败那条路径。

刻意不用 HTTPS:板子只有 8MB Flash、没有 PSRAM,TLS 握手要一次性拿 30~40KB 连续堆,
省下的 RAM 比省下的那点安全值钱。所以只能用**明文 HTTP 且不需要鉴权/签名**的数据源。
虎扑评分满足这个条件,但它是 37 个球员节点、每人一次请求,设备直接抓不划算——留给
电脑侧脚本抓完再经局域网 HTTP 喂给设备(见「虎扑数据」)。

## 比赛日

看板按**北京时间的日历日**分组,与国内赛程表一致:北京时间 11-01 早上 03:00 开打的比赛
算 11-01 的比赛。顶栏显示的就是这个日期,详情页写成「比赛日 11-01」。

接口本身按**美东日期**分桶,所以两者差一天——北京比美东快 12~13 小时,美东傍晚开打的
比赛在北京是第二天早上:

```
北京 T 日的比赛  <->  ESPN 分组 T-1
```

实测(2026-10-31):ESPN 分组 `10-31` 的 7 场全部落在北京 `11-01 03:00~08:30`,而分组
`11-01` 的 4 场全在北京 `11-02`。

- 取数时先按 `T-1` 拼 `dates`,再按开球时间把不属于 T 的场次过滤掉(`nba_board_keep_day`)。
  分组里偶尔会混进前一天(北京)的场次,过滤一次最稳。
- 过滤后一场不剩时才补抓 ESPN 的 `T` 分组:美东中午前开打的比赛(伦敦赛、墨西哥城赛之
  类)在北京是同一个日历日。这种情况罕见,平时不会多发请求。
- 锚点是设备时钟换算出的北京「今天」(`nba_date_today_beijing`),设备跨过午夜后自动跟上。
- 未对时的时候才退回不带 `dates` 的请求(服务端给「最近一个有比赛的日子」),再用首场
  比赛的开球时间反推锚点——接口本身不返回「这属于哪一天」。
- 长按上/下按锚点前后翻,范围 −14 ~ +7 天。
- 接口只接受单日,**不接受区间**:`dates=A-B` 会直接返回 HTTP 400,所以翻日只能一天一发。
- 当天一场比赛都没有时(休赛日,或这一天的场次全在北京次日凌晨):先看补抓结果——
  美东"当天"分组的场次几乎必然属于北京次日,全部落在同一天时**直接采纳,不再重下**;
  补抓不可用时往后探测最多 3 天(接下来的比赛比打完的更有用),再不行才往前回退
  3 天看历史,并标成琥珀色。这套自动跳转每次开机只做一次,之后完全按用户的翻日操作。

明文 HTTP 是刻意选择:本板无 PSRAM,TLS 握手要和 LVGL、Wi-Fi 协议栈同时抢 30~40KB
连续内部 RAM。该接口在 80 端口返回同样的 JSON。**若将来换成需要鉴权的接口,TLS 就是
必需项,必须重新评估内存预算。**

响应体积 10~240KB(单日通常 10~30KB),不可能整包放进内存。`main/nba_parse.c` 是
流式收集器:`main/nba_json.c` 按分片分词,收集器只保留界面要显示的字段,内存占用与
响应大小无关。

## 球员数据

summary 接口的整份响应约 450KB,但 `boxscore` 是文档的第一个键、只占前 ~25KB,后面
跟着的 play-by-play、胜率曲线等占了 95%。`main/nba_box.c` 读完两队名单就置
`complete`,`main/nba_api.c` 随即断开连接:实测一次抓取只下载 ~25KB,耗时不到 1 秒。

解析要点:

- `statistics[].keys[]` 给出这一场各列的顺序(不同比赛会多出 `teamId` 之类),所以
  12 项统计全都**按名字定位下标**,不能写死 `stats[1]`。
- 复合列(`fieldGoalsMade-fieldGoalsAttempted` 之类)的值是 `4-9` / `12-20`,要拆成命中/出手两段;
  `plusMinus` 是 `+26` / `-17`,符号必须保留——直接按无符号解析会把 `-17` 读成 17。
- `didNotPlay` 为真或整行 0 的球员会被剔除,其余按得分降序排列,每队最多显示 10 人。
- 球员名用 ESPN 的 `shortName`(`T. Camara`),原样保留「名缩写在前后接姓」的语序,
  不做重排;并丢掉非 ASCII 字节:LVGL 的 Montserrat 没有 `ć/š/ü` 这类字形,
  留着只会显示成方框。名字列 124px 单行显示,姓名和数值都按实际字形宽度在
  14 / 12 / 10px 里挑一个放得下的字号(`nba_ui.c` 的 `fit_font`),绝不折行——
  行高只有 20px,一旦折行,整块姓会落到第二行被裁掉。右侧 3 列各 32px、
  列间距 4px:投篮组会出现 `12-20` 这类「两位数-两位数」复合值,14px 下
  实占 35px,旧版 26px 列宽会把它裁成 `2-20`。降字号后两头的两位数都完整,
  常规值(`+26` 约 25px)仍是 14px 大字。
- 接口给的两队顺序按 `displayOrder`,不保证客队在前;用比对客队缩写的方式对齐。

## 虎扑数据(电脑侧脚本)

ESPN 给的是英文缩写和英文人名,虎扑给的是中文队名/人名、更全的技术统计。这条数据
不进设备,由电脑上的 `tools/hupu_scrape.py` 抓(纯标准库,不需要登录):

```text
python3 tools/hupu_scrape.py 2026-11-01              # 打印当天 7 场:中文名单 + 最亮评论
python3 tools/hupu_scrape.py 2026-11-01 --game 169027 --json /tmp/g.json

# 球员评分:每队取几人由 --per-team 控制(每人一次请求),每队 4 人全天约 40 秒、37KB
python3 tools/hupu_scrape.py 2026-11-01 --ratings --per-team 8 --json /tmp/score.json

python3 tools/hupu_scrape.py 2026-11-01 --serve 8787 # 局域网 JSON,默认 http://<IP>:8787/hupu.json
```

它抓三张**服务端渲染**的页面,再加上评分接口:

| 页面 | 拿到什么 |
| --- | --- |
| `nba.hupu.com/games/<日期>` | 当天比赛:中文队名、比分、虎扑比赛 id |
| `nba.hupu.com/games/boxscore/<id>` | 单场技术统计:中文人名 + 时间/投篮/三分/罚球/前场/后场/篮板/助攻/犯规/抢断/失误/封盖/得分/正负值 |
| `bbs.hupu.com/<tid>.html` | 帖子 `__NEXT_DATA__` 里的 `lights` —— 按亮数排序的评论,即「高赞评论」 |
| `games.mobileapi.hupu.com/1/8.2.99/bplcommentapi/...` | 评分:每名球员的平均分、评分人数、评分分布、最亮的一条评论 |

几个实现要点:

- 帖子没有固定 id,先在两队分区列表里按「两队名都在标题里 / 标题带本场比分 /
  带赛后·全场·热线 + 一个队名」筛候选,再挑楼里最亮那条评论最亮的帖;标题写了
  别的比分的一律排除(「[赛后]火箭132-100雄鹿」不算骑士-雄鹿)。
- 表尾的「统计」「命中率」两行不是球员,单独放进 `totals` / `shooting`。
- 复合值 `4-11`(命中-出手)、`40.8%` 保持字符串,纯整数转成 int。

### 球员评分:能拿到,而且不要签名

以前记录过「评分只在 App 里、接口要签名」,那是踩错了接口前缀。评分走的是另一组
`bplcommentapi` 前缀,**不校验签名**,版本号换成 `1/8.2.99` 即可(实测 `1/6.7.0`
到 `1/8.2.99` 都通,`1/8.0.0/nba/*` 那组才是 102)。

三跳链路:

```text
m.hupu.com/nba/schedule                     近 7 天赛程,给中文队名 + matchId(约 190KB HTML)
m.hupu.com/nba/live/<matchId>               307 → detail.html?...&outBizNo=8876    ← 评分节点 id
score_tree/getCurAndSubNodeByBizKey         两队名单 + 每人分/板/助/时间/正负(37 人)
  ?outBizType=basketball_match&outBizNo=8876
score_tree/getSelfByBizKey                  个人评分 9.8 / 48965 人 / 高分评论
  ?outBizType=basketball_item&outBizNo=<球员 bizId>
```

踩过的坑:

- `m.hupu.com` **必须用移动端 UA**。桌面 UA 会被 307 到你贴的那个
  `bbsactivity.hupu.com/pc-viewer/?t=...`,而它只是个把 `m.hupu.com/...` 塞进
  `<iframe>` 的壳(外加一个二维码),壳本身不含任何数据;跨域也读不到 iframe 内容。
- 列表接口 `getCurAndSubNodeByBizKey` 里的 `scoreAvg` **时有时无**(同一 URL 反复
  请求会返回 `null`),所以评分一律单独问一次 `getSelfByBizKey`,那边稳定。
- `m.hupu.com/nba/schedule` 只回一个以今天为中心的 7 天窗口,`?date=` 不认参数。
- 评分节点里还有 `coach` / `referee`,比赛看板只要 `type=player`。
- 每人一次请求,所以每队按上场时间取前 N 人再取评分;设备一屏也就显示得下这些。


## Wi-Fi 配网

凭据存在 NVS(命名空间 `nba_cfg`),不打印、不编进固件。**日常用手机配,不需要电脑。**

### 手机配网(主路径)

设备开一个临时热点,手机连上去后浏览器填 Wi-Fi 名称和密码:

```text
1. 设备屏幕显示:热点 NBA-Board,地址 192.168.4.1
2. 手机连上 NBA-Board(开放热点,无密码)
3. 浏览器打开 http://192.168.4.1
4. 选/填 Wi-Fi 名称与密码 → 连接
5. 手机显示「已连接,凭据已保存」,设备自动关热点、切回看板
```

四个入口会打开这个热点,覆盖从「第一次上电」到「连上了却上不了网」的全过程:

| 入口 | 触发条件 |
| --- | --- |
| 首次上电 | NVS 里没有凭据,开机直接进配网页 |
| 换 Wi-Fi 环境 | 有凭据但连续 90 秒连不上(旧网络不在了/改了密码),自动转配网 |
| 外网被认证页拦截 | 连着 Wi-Fi 却持续 3 分钟拿不到 ESPN 数据,自动转配网(本次上电只自动开一次) |
| 手动重开 | 总览页长按确定(没凭据或无法上网时);或串口 `wifi -p` |

第四条是给 Portal 网络的逃生口。这类网络 DHCP 正常、`wifi_mgr` 状态永远是
`CONNECTED`,既不会进 `FAILED` 也不会 `all_failed()`,只看连接失败的看门狗
永远等不到它;早期版本因此会卡在「无法上网」却开不了热点,只能接串口换网。

几个刻意的设计:

- **先试连、后落盘。** 页面提交的 SSID/密码不直接写 NVS,而是切到 APSTA 用 STA 接口
  真连一次,拿到 IP 才保存。手输密码打错一个字符是常态,若先存后试,一次错字就会把
  设备锁死在「新配置连不上、旧配置也没了」的状态,只能再配一次。失败时旧凭据原样保留。
- **热点只开 10 分钟。** 没人配就自动关掉回看板,白开着费电还容易被邻居看见。
- **开放热点、无密码。** 配网窗口很短,加密码反而挡住自己;页面只能提交 Wi-Fi 凭据,
  不暴露设备上的任何数据。这是一台个人设备的取舍,不是通用安全设计。
- 配网期间关掉 `wifi_mgr` 的自动重连:APSTA 下 STA 取不到目标网络会不停断开重连,
  把射频和事件循环占住,还会和配网页的试连抢同一个 STA 接口。

### 为什么不是蓝牙

蓝牙配网(BLUFI 或 ESP-IDF 的 BLE provisioning)都能做,但这块板子是 ESP32-C3、无 PSRAM,
LVGL 已经静态占掉 64 KB 池,DRAM 只剩 114 KB(实测 `idf.py size`):

| 方案 | 额外协议栈 | 结论 |
| --- | --- | --- |
| 热点 + 网页 | 约 25 KB(HTTP 服务 + AP 缓冲) | 采用。手机零安装,任何系统都行 |
| BLE + wifi_provisioning | NimBLE 约 40 KB + mbedtls | 余量偏紧 |
| BLUFI(官方小程序) | Bluedroid 约 80 KB | 无 PSRAM 下风险最高 |

参考 `docs/reference/phoenixzhc/softap-provisioning-and-resource-budget.md`:同类固件在
启动音频子系统后,**最大连续空闲块只剩约 13 KB**,AP 直接起不来。这块板子没有音频,
但道理一样——配网模块必须是最后一个上的,而且要有明确的开/关归属。

### 串口配网(开发备用)

刷机时顺手配、或者想注入按键看页面,走 USB 串口控制台:

```text
nba> wifi                  # 查看状态与语法
nba> wifi MyHome 12345678  # 保存并连接(最多 4 组,同名只更新密码)
nba> wifi -l               # 列出已保存的网络
nba> wifi -d MyHome        # 忘掉一个已保存的网络
nba> wifi -p               # 开启手机配网热点
nba> wifi -c               # 清除全部已保存凭据(并自动转去配网)
nba> key ok                # 注入一次按键(ok/up/down/long-ok/long-up/long-down)
```

最多保存 4 组 Wi-Fi。启动时优先连"上次连通的那个",失败会自动轮换其它已存网络;
轮换全部失败并持续 90 秒才转配网,不会把多网络之间的短暂失败当成彻底没网。
外网认证页另有一条独立计时(3 分钟),不与连接失败共用,原因见上表。
手机配网页提交的新网络也进同一张表,已有同名网络只更新密码。

`key` 命令走的是和真按键完全相同的入队路径,只是不经过 ADC。三个物理键不好按准、
而且插着 USB 看日志时更别扭,调试界面时用它把四个页面走一遍最省事。

用 `idf.py monitor` 或任意 115200 8N1 串口工具连接 USB-JTAG 即可进入控制台。

### 配网页

`main/nba_prov.c` 建立热点与 HTTP 服务,页面内联在固件里(约 1.8 KB,放 flash 的
`.rodata`,不占 DRAM),不引任何外部资源:手机连的是一个没有上行网络的热点,CDN 链接
只会转圈。

| 路由 | 作用 |
| --- | --- |
| `GET /` | 配置表单,内嵌 `fetch('/scan')` 自动填充 Wi-Fi 名称候选 |
| `GET /scan` | 扫描周边 Wi-Fi,返回 JSON 数组(最多 8 个) |
| `POST /save` | 试连并在成功后保存,返回「已连接」或「连接失败」页 |

表单体上限 256 字节,超长直接 413;`Content-Length` 缺省视为错误。设备屏幕上同时显示
热点名和地址——这两个信息只存在于屏幕上,手机里查不到。

联网后由 SNTP 对时(`ntp.aliyun.com`),固件使用 `TZ=CST-8`。
未对时之前,详情页隐藏开赛时间,而不是显示 1970 年的时间。

## 中文与字体

界面中文使用 `assets/fonts/app_font_cjk_16.c`:用 `lv_font_conv` 从 Noto Sans SC
(SIL OFL 1.1)生成的 16px/4bpp 子集,`symbols` 列了 104 个非 ASCII 字符(实际出现在
屏幕上的 70 个由`check_font_coverage.py`核对)。
**没有**使用 LVGL 内置的 CJK 子集——它缺少看板必用的字(例如「赛」「板」「详」
「选」),用了会直接显示成方框。数字与拉丁字母使用 Montserrat 14/20/28/40。

`tools/check_font_coverage.py` 只核对**会上屏**的字面量:`ESP_LOGx` 所在行会被整行
剔除。串口日志不经过 LVGL,若把它算进去,一句日志多写几个字就会报缺字形,逼着往
字体里塞永远不上屏的字。

`tools/check_font_coverage.py` 会抽取两个产出屏幕文本的源文件里所有非 ASCII 字符,
逐字核对字体的字形表,缺字直接让门禁失败,而不是到设备上才变成方框。重新生成字体的
步骤见 [`assets/README.md`](../../assets/README.zh_CN.md)。

## 运行时内存

两个上限都来自真机实测,不是估算:

| 项 | 值 | 说明 |
| --- | --- | --- |
| `CONFIG_LV_MEM_SIZE_KILOBYTES` | 64 | LVGL 自管的内置堆,独立静态区,不与系统堆共享。三个页面(总览 4 行 + 详情 + 球员 8 行)共约 140 个对象,开机日志实测 `39528/60112` 字节,最大空闲块 20584 字节;最早只有两个页面时用默认 24KB 就在建到后段时返回 NULL,踩进 LVGL 断言里的 `while(1)`,外部只能看到看门狗超时。 |
| `NBA_JSON_STACK_MAX` | 24 | JSON 分词器的容器栈深度。 |
| `NBA_PARSE_DEPTH` | 取 `NBA_JSON_STACK_MAX` | 收集器的容器栈,编译期断言保证不比分词器浅。单个比赛日响应实测最深 15 层(`events[] > competitions[] > competitors[] > leaders[] > leaders[] > athlete`),固定成 12 会把合法响应判成语法错误。 |
| `NBA_BOX_DEPTH` | 取 `NBA_JSON_STACK_MAX` | 球员数据收集器的容器栈,同理。 |

对象创建失败时 `main/nba_ui.c` 会打印一次「LVGL 堆不足」并跳过后续布局,不会继续把
空指针喂给 LVGL。

## 已知限制

- 翻日范围是基准日 −14 ~ +7 天;看更早的赛季需要改 `DAY_OFFSET_MIN`。
- 比赛日按北京日期划分;ESPN 把美东中午前开打的比赛算进同一天的 ESPN 分组,这类场次
  (伦敦赛等)只有在主分组过滤后为空时才会被补抓回来。
- 一个比赛日超过 16 场时只显示前 16 场(受 `NBA_MAX_GAMES` 与接口 `limit` 限制;NBA 单日上限 15 场,正常不会触顶)。
- 球员页每队只列前 10 人(按得分排序),12 项统计都是原始计数,不折算命中率,也没有
  进攻/防守篮板的分项。
- 球员数据在进入球员页时抓一次,不随 60 秒刷新更新:比赛进行中想刷新需要退出再进入。
- 队名与球员名用英文缩写/英文名;中文译名需要大得多的字形子集,所以中文数据目前只在
  电脑侧脚本里,没上屏。
- 虎扑球员评分能抓(免签名的 `bplcommentapi`),但每人一次请求,只放在电脑侧脚本里;设备要看需要走 `--serve` 的局域网 JSON。
- 没有逐回合战报、球队数据与排名。
- 需要网页认证的 Wi-Fi 无法在设备上完成登录,只能放行 MAC 或改连免认证网络。
- 比分来自第三方公开接口,无 SLA;接口结构变化会表现为「刷新失败」,屏幕保留上一份数据。
